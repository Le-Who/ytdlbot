# План единовременного обновления загрузки медиа

> Для исполнителя: использовать executing-plans; реализацию начинать после согласования пользователем. До этого изменяется только документ плана.

**Цель:** уменьшить задержки и зависимость от cookies, прокси и ресурсов VPS, добавив бесплатные внешние источники, параллельный поиск равнозначных результатов и повторную отправку через Telegram file_id.

**Приоритет пользователя:** YouTube Shorts и обычные YouTube-видео — основная функция и отдельный обязательный критерий приёмки. Успех TikTok/Instagram не компенсирует неработающую загрузку YouTube. Сначала закрывается YouTube-маршрут, затем остальные расширения; публикация остаётся единовременной.

**Профиль доставки:** production использует локальный Telegram Bot API. Основной предел одного загружаемого файла — 2000 MB; облачные ограничения 20/50 MB относятся только к аварийному режиму без локального API и не должны определять качество, разрезание или сжатие штатной загрузки.

**Поправка по фактической конфигурации:** локальный API способен принимать 2000 MB, но текущий deploy.yml при каждом деплое записывает MAX_TG_UPLOAD_MB=900 и MAX_DL_MB=1000. Следовательно, поддержку 2000 MB необходимо довести до всей цепочки и убрать переопределение из deploy-скрипта; одной настройки config.py недостаточно.

**Архитектура:** единый MediaPipeline для сообщений, групп, команд, callback и HTTP-загрузок. Независимые провайдеры возвращают кандидатов; планировщик проверяет соответствие запросу и выбирает первый пригодный результат. Получение метаданных, скачивание, преобразование и доставка имеют отдельные ограничения ресурсов.

**Стек:** существующие Python 3.12, asyncio, FastAPI, python-telegram-bot, curl_cffi, Redis/MemoryStorage, yt-dlp, gallery-dl, ffmpeg; без обязательного нового сервера, платного API или прокси.

**Спецификация:** требования пользователя в текущей задаче и решения этого документа. Весь функционал выпускается одним согласованным релизом; этапы ниже — порядок разработки и проверки.

## Основания и границы проверки

- Исходный коммит: 5c1aaa1. Изучены маршруты сообщений/групп/команд, оркестратор, загрузчики, отправка, очереди, кеш, конфигурация, Docker и CI.
- Автодеплой уже существует: push в vps запускает Deploy to VPS. GitHub Actions показывает пять последних успешных запусков; последний от 2026-06-20 для текущего HEAD 5c1aaa1: https://github.com/Le-Who/ytdlbot/actions/runs/27862952734 . Это подтверждение исполнения workflow, не проверка текущего состояния VPS.
- Изучены соседние gemaibotv2 и crab-rave. Gemaibotv2 развёртывает SHA-образ после успешного CI; crab-rave использует scoped deploy, проверку свежести SHA, flock, readiness с версией и rollback. Их файлы не изменялись.
- 75 выбранных тестов прошли на локальном Python 3.14. Это не полный прогон, не проверка production и не замена проверкам целевого Python 3.12.
- В отдельном локальном воспроизведении отменённый участник DownloadQueue остался в очереди; освобождение активного слота передало его отменённой задаче, свободных слотов осталось 0.
- TikWM вернул code=0 и медиассылку без аккаунтных cookies. SSSTik вернул медиассылки; Range-запрос прочитал 65536 байт, HTTP 206, обнаружена сигнатура MP4. Полная декодируемость и заявленное качество этим не подтверждены.
- FxTwitter OpenAPI доступен; контрольный пост вернул NOT_FOUND. VXTwitter в контрольном запросе не вернул JSON. Они не прошли полную проверку скачивания.
- Vevioz вернул метаданные и качества YouTube; его текущий SDK требует X-Turnstile-Clearance при создании job. Фоновая загрузка без участия пользователя не подтверждена.
- Измерения выполнены с текущего компьютера, а не с IP действующего VPS. Никакие заявленные ниже бюджеты не являются измеренным ускорением production.

## Глобальные ограничения

- Нулевые платежи: запрещён автоматический переход на платные тарифы; никаких обязательных пробных кредитов.
- Локальный Bot API — обязательный production-компонент, а не необязательная оптимизация. Целевой единый MAX_MEDIA_FILE_MB=2000 заменяет прежние разрозненные ограничения; конфигурация не должна молча возвращаться к пределу 45/50 MB.
- Обычные публичные ссылки обрабатываются без персональных cookies. Существующий авторизованный Instagram-путь остаётся отдельной опцией для случаев, которые публичные провайдеры не обслуживают.
- Максимум две одновременные внешние попытки получения кандидатов на один запрос; максимум один тяжёлый локальный extractor на запрос.
- Основная передача файла одна; вторую разрешать только как ограниченную попытку при задержке/зависании, с общим лимитом трафика и диска.
- Не менять выбранные пользователем качество, аудиорежим, фрагмент или полноту альбома скрытым fallback.
- Сторонним провайдерам не передаются Telegram-токены, персональные cookies, API-ключи других провайдеров и локальные пути.

## 1. Провайдеры и матрица маршрутов

### Основной набор

| Платформа | Одновременные лёгкие попытки | Резерв |
|---|---|---|
| TikTok | TikWM + SSSTik | Рабочий Cobalt; затем один yt-dlp или gallery-dl по типу материала |
| X/Twitter | FxTwitter + доступный Cobalt | yt-dlp; VXTwitter только после успешной проверки |
| Instagram public | Прошедший проверку SnapSave + доступный Cobalt | gallery-dl/yt-dlp; действующий Instagram session provider при наличии сессии |
| Facebook public | Прошедший проверку SnapSave + доступный Cobalt | yt-dlp |
| Pinterest | Native provider + доступный Cobalt | gallery-dl/yt-dlp |
| YouTube / Shorts | yt-dlp/Deno/EJS/PO-token сразу + проверенный независимый бесплатный внешний источник сразу при доступности | Резервный внешний источник по отдельному лимиту; cache file_id до любых запросов |
| VK/RuTube и остальные | Существующий yt-dlp | Только провайдеры с подтверждённой поддержкой конкретной платформы |

Если внешнего провайдера нет или он выключен, не ждать его искусственный timeout. FxTwitter проверяется на свежем существующем посте перед включением.

### Приоритетный блок YouTube / Shorts

- Нормализовать `youtube.com/shorts/{id}`, `watch?v={id}`, `youtu.be/{id}` и мобильные ссылки в один media_id. Параметры начала/конца фрагмента сохранять отдельно; служебные tracking-параметры не разделяют кеш.
- При отсутствии file_id запускать локальный YouTube-путь сразу, без 1.5 s ожидания. Параллельно запускать прошедший проверку внешний источник; не считать разные player_client на одном VPS независимостью от блокировки его IP.
- Разделить успех получения метаданных, скачивания видеопотока, получения аудиопотока, объединения и фактической отправки. Приёмка требует полного последнего этапа.
- 720p и 1080p со звуком — обязательные варианты проверки при наличии у оригинала. Раздельные video/audio потоки объединять через stream copy, если кодеки совместимы; не ограничивать результат только заранее объединёнными форматами.
- Для Shorts сохранять вертикальную ориентацию и соотношение сторон. Нормализовать профиль качества с учётом ориентации и фактических width/height: кадр 1080x1920 нельзя отвергать как превышающий горизонтальный лимит height<=1080 или скрыто уменьшать до 608x1080.
- Для /mp3 и клипов применять ту же маршрутизацию. Качество, аудиодорожку/язык и интервал включить в ключ кеша и проверку эквивалентности.
- Повторить извлечение при истёкшем подписанном media URL в общем бюджете, без бесконечных повторов прежнего CDN-адреса. При 403/bot-check быстро передать приоритет независимому внешнему источнику, если он имеется.
- Отправлять файлы размером до 2000 MB через уже установленный Local Bot API без скрытого разрезания, сжатия или уменьшения качества. Облачный режим проверять лишь как явно ограниченный аварийный профиль.
- Проверка бесплатного внешнего YouTube-источника остаётся незакрытой частью выбора решения: требуется полная загрузка с production IP без cookies/прокси/платежей/ручной CAPTCHA. Одной работающей веб-страницы, метаданных или Cobalt healthcheck недостаточно. До этой проверки не утверждать, что зависимость YouTube от IP VPS устранена.
- Дополнительная проверка кандидатов: Tunelio даёт только 100 пробных credits, затем платные планы; Vid Kraken публикует платные планы и бесплатную пробу без подтверждённого постоянного бесплатного лимита. Оба исключены из обязательного бесплатного решения. Loader.to в контрольной проверке веб-инструмента не открылся; старый неофициальный wrapper не считается доказательством актуальной работоспособности.
- Сначала сформировать контрольный набор из 12 публичных Shorts и 12 обычных видео: вертикальные/горизонтальные, короткие/длинные, 720p/1080p, раздельные потоки, несколько аудиодорожек, свежая публикация, файл больше 50 MB. Прогнать с VPS в трёх временных окнах, отдельно с холодным и тёплым кешем.
- В отчёте выделить Shorts и обычные видео: доля полной доставки, p50/p95, причины 403/429, расход трафика/CPU и успешность независимого маршрута. Длительность загрузки длинного видео не ограничивать 20 s бюджетом поиска кандидатов: материализация имеет отдельный deadline и stall timeout.
- Дополнительно воспроизвести отказ локального extractor, отказ внешнего источника, истечение CDN URL, отсутствие звука, неверную ориентацию и отмену объединения. Проверить, что резерв срабатывает до завершения тайм-аута зависшего первого источника.

### Решения по внешним сервисам

- **SSSTik:** добавить HTTP-адаптер: получить страницу, извлечь текущий session token (при проверке это s_tt), отправить форму, разобрать медиа. Не копировать устаревший regex для tt. Временная веб-сессия создаётся автоматически, пользователь её не обслуживает. HTML/JS — изменяемый протокол, поэтому нужны fixtures и быстрое отключение адаптера.
- **TikWM:** сохранить бесплатный веб-endpoint; лимиты хранить в конфигурации, учитывать 429/Retry-After. Комментарий о 5000 запросах/сутки не считать подтверждённой текущей квотой. Отдельный tikwmapi.com не подключать на платном тарифе.
- **FxTwitter:** добавить /2/status/{id}, нормализацию видео, фото, анимаций и нескольких вложений. Публичная документация указывает 1000 запросов/мин/IP; установить более консервативный внутренний лимит.
- **Cobalt:** сохранить поддержку внешних экземпляров; бесплатный работающий endpoint и доступ проверять до включения. Не считать api.cobalt.tools гарантированно открытым. Хранить capabilities, ключ и ограничения отдельно для каждого точного origin. Каталоги экземпляров использовать для проверки кандидатов, а не для автоматического доверия произвольным адресам.
- **SnapSave:** приоритетный кандидат веб-адаптера для Facebook/Instagram. Бесплатная форма и готовая библиотека snapsave-media-downloader существуют, но полное скачивание не проверено. Реализовать адаптер в этом релизе только после контрактной проверки; при необходимости перенести HTTP-протокол в Python, без отдельного Node-сервиса. Поддержать различие готовой ссылки и задания upstream-render.
- **FastDL / sssInstagram:** резервные кандидаты для public Instagram. FastDL публикует API-раздел, но доступ выдаётся через контакт, бесплатность API не подтверждена. Бесплатную веб-форму считать отдельным вариантом; не обещать документированный бесплатный REST API.
- **SaveFrom / SSYouTube:** не делать основной зависимостью релиза. Не удалось подтвердить актуальный бесплатный машинный интерфейс и полный путь скачивания. Отсутствие такой проверки не означает техническую невозможность интеграции.
- **Vevioz:** не включать в автоматическую гонку: подтверждённая выдача метаданных не снимает Turnstile на создании файла. Возможный ручной переход через кнопку — отдельный режим, не успешная доставка ботом.
- Не добавлять self-hosted Cobalt/Invidious/Piped, browser farm и новые proxy-сервисы в обязательную инфраструктуру этого релиза.

## 2. Единый контракт и маршрутизация

Создать `app/services/media/models.py`, `registry.py`, `pipeline.py`, `race.py`, `validation.py`, `transport.py`, `delivery.py`; адаптеры — `app/services/media/providers/`.

Контракт:

```python
class MediaProvider(Protocol):
    def supports(self, request: MediaRequest) -> bool: ...
    async def resolve(self, request: MediaRequest) -> list[MediaCandidate]: ...

class MediaPipeline(Protocol):
    async def resolve(self, request: MediaRequest) -> ResolvedMedia: ...
    async def deliver(self, request: MediaRequest, target: DeliveryTarget) -> DeliveryReceipt: ...
```

- `MediaRequest`: canonical URL/platform/media_id, media kind, quality policy, audio format, clip interval, album selection, watermark policy, caller scope, общий deadline.
- `MediaCandidate`: provider/backend family, media identity, ordered items/variants, dimensions/duration/codecs, declared bytes, URL/expiry, request headers, auth scope, remote-processing flag.
- `ResolvedMedia`: кандидаты, прошедшие проверку, реальный набор доступных вариантов, состояние полноты метаданных. Не объединять несовместимые provider format_id.
- `DeliveryTarget`: bot_id/chat_id/topic_id, reply context, caption preferences.
- `DeliveryReceipt`: success/failed/uncertain, Telegram message IDs и file IDs по типу вложения, фактически доставленные параметры.
- Провайдеры не отправляют сообщения в Telegram и не решают пользовательские предпочтения.
- Перевести `messages.py`, `group_logic.py`, `commands.py`, `callbacks.py`, `ig_callbacks.py`, `api/routes.py` на общий pipeline. Сначала оставить совместимые обёртки существующих сервисов, затем убрать дублирующие ветки.

## 3. Гонка равнозначных результатов

- [ ] Сначала искать подходящий Telegram file_id и существующую общую задачу по ключу запроса.
- [ ] На cache miss одновременно запустить два подходящих дешёвых провайдера; исключить неизвестные/недоступные capabilities и открытый circuit breaker.
- [ ] Стартовые бюджеты: connect 3 s, одна попытка resolver 8 s, общий поиск кандидатов 20 s. Локальный резерв запускать через 1.5 s без пригодного кандидата, если имеется ресурсный слот; не ждать ошибки первого.
- [ ] Retry допускается только для временной ошибки и в оставшемся общем бюджете. Retry-After длиннее бюджета завершает участие провайдера в текущем запросе.
- [ ] Проверять media identity, тип, интервал, звук, качество, отсутствие водяного знака при соответствующем запросе, количество и порядок вложений. Неизвестное качество требует проверки, а не выигрывает автоматически.
- [ ] HTTP 200 или JSON со ссылкой — лишь кандидат. Проверить редиректы, срок жизни, сигнатуру контейнера и доступность ограниченным Range-запросом; после получения файла проверить ffprobe, размер и необходимые потоки.
- [ ] Начать одну передачу лучшего подходящего кандидата. Если нет первого байта 1.5 s либо нет прогресса 3 s, при наличии бюджета разрешить второй поток. Первым результатом считать полностью полученный и проверенный эквивалентный материал.
- [ ] Два полных исходящих скачивания по умолчанию разрешены только для файлов с известным размером не больше 20 MB каждый. Это ограничение лишнего трафика между медиапровайдерами, а не лимит Telegram. Для более крупных файлов параллельны resolver и пробы, полная передача одна, переключение по stall timeout; выбранный файл затем может быть отправлен через Local Bot API вплоть до 2000 MB.
- [ ] До подтверждения пригодности основного файла сохранить резервные кандидаты. После выбора отменить проигравшие операции, закрыть сокеты, завершить процессные группы и удалить partial-файлы.
- [ ] Отправляет один delivery worker. Сбой отправки с неизвестным исходом записывать как uncertain, не рассылать автоматически дубликаты. Telegram не предоставляет универсальную exactly-once гарантию.
- [ ] Если результат слабее выбранного качества, предложить его отдельно. Для точного режима не подменять 1080p на 720p, MP3 на M4A или карусель на один файл.

## 4. Кеш и минимизация нагрузки

- [ ] Создать `app/core/media_cache.py`: bot_id + canonical media_id + output kind + quality + clip + album item/order + transform version + auth scope.
- [ ] Изменить `sender.py`: возвращать DeliveryReceipt вместо bool. Хранить video/audio/photo/animation/document file_id и не менять Telegram-тип при повторной отправке.
- [ ] Кешировать public media между пользователями; авторизованные результаты изолировать. Сохранять на 30 дней с продлением при использовании; невалидный file_id удалять и получать файл заново.
- [ ] Разделить стабильные метаданные, короткоживущие CDN URL и Telegram file_id. Не хранить путь к временному info.json как долговечные метаданные.
- [ ] Ввести singleflight для resolve и materialize: повторные запросы подписываются на одну задачу. Отмена одного подписчика не отменяет работу остальных. Redis lease имеет owner token, expiry и безопасное освобождение; без Redis использовать memory-вариант.
- [ ] Прямую отправку URL применять только при подтверждённой совместимости MIME, размеров и доступа без специальных headers. Возможность upload 2000 MB не доказывает такой же предел server-side URL fetch. Local Bot API скачивает URL на том же VPS, поэтому это не устранение трафика VPS. Основной путь крупных файлов — общий локальный путь; multipart остаётся совместимым резервом после проверки bounded-memory поведения клиента.
- [ ] Ошибку URL-fetch обрабатывать переходом к потоковой локальной загрузке. HEAD не считать достаточной проверкой, при отсутствии длины использовать ограниченную пробу и строгий byte cap.
- [ ] Убрать накопление полного resp.content для крупных файлов. Использовать ограниченные буферы, streaming во временный файл, reservation диска и отдельные семафоры resolver/download/conversion/upload.
- [ ] При нехватке диска продолжать доставлять уже известные file_id; запрещать только работу, требующую недоступного ресурса. Janitor не удаляет файлы с активным lease.

## 5. Исправления существующей реализации

| Место | Изменение и причина |

### Обязательные исправления профиля Local Bot API

- Добавить project-scoped media volume с одинаковым абсолютным путём /srv/ytdlbot/media в bot (rw) и tg-api (ro); проверить UID/permissions. Настроить base_url, base_file_url и local_mode согласованно с установленной версией PTB. Передавать локальный путь, хранить файл до завершения отправки и удаления lease. Это основная доставка крупных файлов без загрузки 2 GB в RAM Python. Действующий multipart оставить как резерв, проверив, что библиотека не читает весь файл в память. Сегодня volume не общий и file://-опция не используется вызывающим кодом.
- Ввести единый MAX_MEDIA_FILE_MB=2000 (MB = 1 000 000 байт) для скачанного и итогового файла; legacy MAX_DL_MB/MAX_TG_UPLOAD_MB мигрировать с явной валидацией. Удалить запись 900/1000 из deploy.yml. При mux/transcode учитывать отдельно объём исходных дорожек и временного результата. Меньший операторский предел допустим только как явная политика, отражённая в health.
- Удалить 48.5/50 MB как условие штатного split/compress, когда локальный API здоров. Сохранить проверку фактического размера против 2000 MB до скачивания при известных metadata и во время потоковой записи.
- Увеличить и сделать настраиваемыми `read_timeout`/`write_timeout` отправки: текущие 120 s могут оборвать большой файл задолго до достижения 2 GB. Timeout считать по отсутствию прогресса, а не по общей длительности передачи.
- На старте выполнить функциональную проверку локального endpoint и зафиксировать активный delivery profile в health/metrics. Если локальный API недоступен, не применять скрыто правила облачного режима к уже выбранному большому файлу: остановить приём тяжёлых задач и сообщить о временной недоступности либо использовать явно включённый cloud fallback только для подходящих файлов.
- Размер временного файла и свободный диск остаются реальными ограничителями. Резервировать объём до скачивания, учитывать одновременные задачи и проверять диапазон 1–2000 MB; лимит Telegram не означает наличие 2 GB свободного диска или достаточного времени загрузки.

Добавить общую политику: оригинальный совместимый файл -> remux -> минимальная необходимая конверсия. Разделение/уменьшение качества не применять скрыто. Если ffprobe не смог подтвердить пригодность, не объявлять файл валидным.

### 7.1. Автодеплой на общем VPS

**Текущее поведение:** push в vps -> build GHCR latest -> SSH /opt/ytdlbot -> переписывание .env -> compose pull всех сервисов -> compose up -d --remove-orphans. Скрипт не перезагружает VPS, но также регистрирует Caddy route, при отсутствии запускает общий Portainer и делает глобальный docker image prune -f. Отдельный test.yml не запускает push-тесты vps; deploy не зависит от тестов. Нет гарантии готовности нового бота, версии релиза и автоматического отката.

**Целевая схема:** push в vps -> обязательные проверки того же SHA -> сборка в GitHub Actions -> GHCR image по SHA и digest -> preflight -> drain -> замена bot -> readiness/version checks -> commit release либо rollback.

1. Объединить gates в deploy workflow или reusable workflow: Python 3.12, полный набор тестов, контрактные/regression-тесты, docker compose config, shell validation и проверка собранного image. Live-проверки чужих сервисов не делать нестабильным обязательным gate каждого push; для первого релиза они обязательны отдельно.
2. Установить deployment concurrency с cancel-in-progress:false и project-scoped flock на VPS. Перед активацией убедиться, что проверенный SHA всё ещё является актуальным HEAD ветки vps; устаревший запуск пропускать. Не выполнять произвольный HEAD вместо проверенного SHA.
3. Передавать immutable digest, APP_RELEASE=SHA и allowlist файлов в /opt/ytdlbot/releases/<sha>. Проверять SSH host fingerprint; secrets не выводить. Сохранить previous image/config/release manifest до переключения.
4. Однократно прочитать Compose labels действующих контейнеров и имена volumes. Закрепить существующий project name; не создавать новый Compose project и новые tg-api/Redis volumes по случайному имени каталога релиза. Проверить владельца и абсолютный путь project root, сеть, порты, дисковый бюджет и local API.
5. Обычный deploy выполняет pull только image бота и compose -p <verified-project> up -d --no-deps --no-build bot с точным digest. Не выполнять compose down, remove-orphans, pull/up всех сервисов, VPS reboot, restart Docker, Caddy reload, установку Portainer и global image prune. Удалять только собственные старые release/image refs после проверки использования; хранить минимум текущую и предыдущую исправную версии.
6. Удалить генерацию полного .env из YAML. Хранить secret values в закрытом project env/secrets-файле на VPS, обновлять только явно управляемые поля атомарно; изменение схемы валидировать. Убрать hardcoded webhook secret, согласованно заменить через secret store и setWebhook. Не возвращать настройки 900 MB, старого Cobalt endpoint и неподтверждённые tuning-параметры при каждом push.
7. Bootstrap и миграции выделить из обычного deploy. В первом согласованном релизе добавить media/state volumes, Deno/EJS и при необходимости обновить закреплённую версию bgutil-pot. tg-api потребуется пересоздать один раз для нового mount, сохранив существующий session volume. Это ограниченное обновление сервисов ytdlbot, не соседних проектов. Redis и host services остаются вне routine deploy; дальнейшие dependency upgrades имеют отдельный явный список сервисов.
8. Добавить /health/live и /health/ready: ready показывает APP_RELEASE, активный upload limit, доступность durable store и обязательного Local Bot API. Отказ необязательного внешнего провайдера не делает весь бот unhealthy. Проверять локальный адрес и публичный route, совпадение SHA и getWebhookInfo; не принимать один HTTP 200 за успешный релиз.
9. При ошибке readiness, неверном SHA или прерывании активации вернуть previous image/config, дождаться его готовности и завершить workflow с ошибкой. Не откатывать Redis/SQLite данные назад; миграции должны быть обратно совместимы с предыдущим релизом. Если rollback тоже не прошёл, остановить цепочку и сохранить диагностические материалы без secrets.
10. Документировать ручной запуск этого же release/rollback скрипта. Автоматическая цепочка после push не требует действий пользователя, кроме существующих GitHub environment protections, если они настроены. Нулевой downtime для единственного bot instance не обещать: ограниченная пауза с сохранением принятых заданий.

### 7.2. Сохранение заданий при обновлении

- Сейчас webhook возвращает 200 после create_task, до устойчивого сохранения работы; остановка контейнера может потерять уже подтверждённое обновление. На shutdown удаляется webhook, что также мешает доставке во время смены контейнера.
- Добавить SQLite WAL в отдельном project-scoped state volume для update inbox, job state, delivery receipts и update_id dedup. Один bot worker/process владеет durable очередью. Текущий Redis allkeys-lru нельзя использовать как единственное хранилище принятых заданий: eviction может удалить их; оставить Redis кешем/ускорителем.
- Webhook подтверждает 200 только после транзакционной записи update; ошибка записи возвращает retryable ответ. Сроки хранения update payload ограничены, запись содержит минимум необходимых данных. MemoryStorage не используется для production-очереди.
- Перед deploy включить drain: перестать брать новые тяжёлые jobs, новые webhook updates надёжно записывать; дождаться активных jobs в ограниченный срок. По deadline сохранить checkpoint, корректно отменить процессы и перенести незавершённую работу на следующий запуск. Временные файлы с lease лежат на постоянном media volume, но resume только после проверки целостности/актуальности URL.
- Не удалять webhook при штатной остановке для обновления. Новый процесс восстанавливает jobs и проверяет тот же webhook URL; не запускать параллельно два polling consumer.
- Известные отправленные элементы не повторять. При неопределённом исходе Telegram-send записать uncertain: автоматическое повторение может создать дубликат и не считается безопасным восстановлением.

## 8. Приёмка и один релиз

- [ ] До изменения кода собрать исходные p50/p95, success rate, RSS, CPU и трафик на одинаковом наборе публичных ссылок с действующего VPS.
- [ ] Контрактные тесты каждого адаптера: успех, 429, timeout, HTML вместо JSON, challenge, истёкший CDN URL, несовместимый кодек, отсутствующий звук, фото/видео/альбом, меньшая доступная версия.
- [ ] Тест гонки: первый провайдер зависает на 15 s, второй возвращает пригодный материал через 1 s; результат не ждёт 15 s. Более быстрый неправильный/повреждённый результат не побеждает.
- [ ] Тест отмены: очередь восстанавливает все слоты; через 2 s после отмены нет принадлежащих запросу subprocess/socket/partial-файлов. Отмена подписчика не ломает остальных.
- [ ] Тест кеша: повторная эквивалентная ссылка использует file_id без внешнего resolver, скачивания и ffmpeg. Другой clip/quality/type/auth scope не получает чужой результат.
- [ ] Тесты Local Bot API в двух контейнерах: multipart без общего volume; `file://` только с общим volume; файлы около 50 MB, 1 GB и логическая проверка границы 2000 MB без обязательной передачи 2 GB в каждом CI; cloud URL/multipart fallback, ограничения диска/RAM, disconnect и неизвестный исход Telegram-send.
- [ ] Проверить все действующие тесты на Python 3.12 с настоящими FastAPI, ffmpeg/ffprobe и Redis; мок отсутствующего FastAPI не считается интеграционной проверкой.
- [ ] Проверить deploy в изолированном Compose окружении: успешная замена, readiness failure/rollback, устаревший SHA, два одновременных запуска, обрыв SSH, отсутствие диска, сохранение секретов/настроек и томов. Контейнеры соседнего тестового проекта и общие службы не перезапускаются.
- [ ] Проверить durable inbox при SIGTERM/SIGKILL: подтверждённый update не теряется; очередь восстанавливается, завершённый delivery не повторяется, uncertain отправка не дублируется автоматически. Проверить drain deadline и сохранение webhook между версиями.
- [ ] Для первого релиза отдельно проверить scoped migration mounts и сохранность tg-api session/Redis volumes; дальнейший обычный push заменяет только bot. Отказ dependency migration также возвращает согласованные прежние image/config без удаления данных.
- [ ] Провести ограниченные live-тесты на публичных видео/фото/альбомах всех платформ, с IP VPS; качество сверять по готовому файлу. Не включать неисправный кандидат лишь ради количества провайдеров.
- [ ] Целевые показатели для сравнения: p95 холодных запросов на платформах с двумя рабочими провайдерами лучше исходного минимум на 25%, доля успешных доставок не хуже, RAM в текущем лимите, CPU не растёт, нет дубликатов из-за гонки. Это критерии приёмки, не обещание измеренной скорости.
